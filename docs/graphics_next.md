# GPU backend integration checkpoint

Verified runtime stop: VdInitializeEngines, called from GH2 0x823D5FA0 with return address 0x823D5FD8. The title has already allocated a 0x2000-byte physical block for its 0x12C0-byte request. The shared physical aliases are tested; no rendering has occurred.

The translated caller registers a title-termination callback next and then calls VdSetGraphicsInterruptCallback at return address 0x823D6000. A successful engine implementation must retain callback state, execute guest interrupt handlers with valid contexts, and provide a GPU command processor. Later VdInitializeRingBuffer uses a physical address and log2 size. Returning success without that backend would only move the diagnostic stop.

Required integration work:
- Adapt an existing Xenon GPU command processor/shader translator to this runtime's memory and guest-call ABI, or implement the required command set.
- GPU writeback alias at 0x7F000000 is now implemented and tested in both directions. Add MMIO handling before command submission.
- Route ring-buffer updates, completion/read-pointer writes and interrupts through the worker-safe runtime.
- Add a native window and actual render-target presentation, then validate a frame generated by GH2.

The source ABI and portable LLVM-MinGW build must be reconciled with any external backend's Windows SDK and compiler requirements. The current binary has no GPU backend dependency and must continue to stop explicitly here until one is available.

## Backend build investigation

Downloaded ReXGlue revision `c94f5ebdcb3c9d1a460ca48e04f9758448f8d518` into ignored `tools/rexglue-sdk`. Its `rexgpu-xenos` target is a dynamic plugin linked to `rexruntime`, not an independent renderer DLL. `SetupGuestGpu` requires the SDK's concrete FunctionDispatcher and KernelState, obtains its Memory from the dispatcher, installs MMIO and creates XHostThread workers. Our PPCContext layout also differs (our VSCR field precedes registers; SDK places its own VSCR/MSR fields elsewhere). Direct context casts are invalid.

The native host probe successfully created a D3D12 device on the RTX 5070 (11943 MiB VRAM, resource binding tier 3, rasterizer ordered views supported). This verifies host device access only, not Xenos rendering.

Build feasibility is being tested with the existing LLVM-MinGW toolchain using `scripts/build_gpu_backend.ps1`. Upstream's documented Windows toolchain is Visual Studio C++/clang-cl. Current local Visual Studio and Windows Kits directories contain no usable compiler/SDK installation. Logs are `build/rexglue_configure.log` and `build/rexglue_build.log` when generated.

Pinned dependency paths downloaded: cli11, libmspack, FFmpeg, tomlplusplus, simde, xxHash, spdlog, fmt, utfcpp, imgui, sdl3, o1heap and inja under the SDK's thirdparty directory. They use the SDK gitlink revisions. Vulkan and optional profiling dependencies are disabled for this first D3D12 build.

## MinGW build compatibility work

Configuration passed with Clang 23.1.3, D3D12 enabled and Vulkan disabled. SDL, FFmpeg utility/codec libraries, core and filesystem targets have compiled during this investigation. `scripts/apply_rexglue_patches.py` guards each change against the pinned source:
- Skip MSVC's legacy CRT-version header on MinGW.
- Use libmspack's actual source directory instead of Windows text representations of symlinks.
- Extend the existing libc++ clock-conversion fallback to this toolchain.
- Retain modern SetThreadDescription while disabling the legacy MSVC debugger exception on MinGW.
- Select Windows 10 declarations and SSE4.1/AVX for relevant SDK targets.
- Supply Microsoft's DXProgrammableCapture header with a MinGW UUID declaration, and correct a `_uuidof` spelling.

The vendored header is from Microsoft's [Win32 metadata SDK headers](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/DXProgrammableCapture.h); its copyright notice is retained. Additional MinGW UUID declarations cover the pinned DXC interfaces. The SDK executable-path lookup uses GetModuleFileNameW, because its DLL's CRT program-name pointer was empty.

The runtime DLL, Xenos plugin and smoke executable now compile and link. The smoke test successfully initializes the real D3D12 device, GPU command worker, GPU VSync worker and GPU MMIO handler on the RTX 5070, then shuts down. Presentation is disabled. See `docs/gpu_backend_validation.json` and `build/rex-smoke-state/gpu.log`. This does not establish a GH2 frame.

## SDK-context GH2 build

`scripts/prepare_rex_runtime.py` prepares a separate copy of the translations in `build/rex-generated`. Its header uses the SDK's actual PPCContext type, rather than casting the original incompatible context. The sticky saturation field uses the SDK's byte-sized VSCR flag. The independent emitted-instruction oracle passed 87 fixtures and 8,700 executions with this context (`docs/rex_instruction_validation.json`).

The candidate `gh2_rex_bootstrap` runs with SDK-owned guest memory, kernel, loader and renderer. Generated indirect calls use the SDK dispatcher. Import adapters resolve module ordinals through the SDK's kernel module registry and register their original guest addresses. Missing implementations halt when used. The original diagnostic runtime remains available for comparison.

Build with `scripts/build_gpu_backend.ps1 -GameRuntime -Python <interpreter-path>`, then run `python tests/check_rex_runtime.py --game`. These are bounded headless diagnostics; presentation, audio and input are subsequent integration work. The SDK smoke check is `python tests/check_rex_runtime.py`.

## First visible output

Latest guitar correction: native subtype preservation alone did not fix highway input. The user's reported A/orange, LB/red and idle LT/green pattern was reproduced by running the actual translated GH2 controller poll (`0x8227B3F0`), which accepts only subtype 7. `runtime/gh2_guitar_compat.h` normalizes guitar subtypes 6/11 to 7 in the generated XamInputGetCapabilities adapter after a successful query. It does not alter button/axis state, ordinary gamepad identity or failed queries. `docs/guitar_scheme_validation.json` records 27 passing fixed guitar polls and the baseline subtype-6 failure. The updated windowed binary was rebuilt and reopened for hands-on verification.

The SDK-context build passed the former GPU-engine blocker, initialized the ring buffer and read-pointer writeback, and reached MMIO command submission. The first attempt read zero-filled buffers: the pinned Windows SDK applies an extra 4 KB host offset to E-range pages, while the original translations indexed the flat base directly. `GH2ReXMemoryBase` now applies that offset to all base-plus-address expressions, including VMX loads/stores. Tests exercise actual SDK allocations and bidirectional CPU/GPU visibility across all three page sizes.

After that fix, the backend translated GH2 shaders, created render targets and ran the game's audio initialization. SDL audio/input were then attached. The headless runner drained callbacks before title termination to avoid an audio callback racing a disappearing dispatch entry.

`Guitar Hero 2.exe` uses the SDK's ReXApp presentation and event loop. Its first successful bounded windowed run rendered the animated GH2 intro. The GPU presenter captured 1280x720 guest output at 15, 30 and 45 seconds, and the second frame was visually inspected. The intro capture is `build/windowed-state/first-intro.png`. This establishes actual game-generated output, not menu navigation, song gameplay or timing accuracy.

Subsequent captures show the save prompt, Quick Play menu, difficulty selection, loading, “Surrender” stage and active note highway. The user confirmed reaching gameplay, then reported wrong fret mappings with an XInput guitar. The SDK defaults to SDL and hardcodes subtype 1 for every SDL controller, while Windows reports this physical guitar as subtype 6. The app and launcher now select native XInput. Capability selection preserves physical guitar subtypes 6/7/11 even when keyboard input is the most recently active device. Raw button/axis values remain unchanged.

`tests/rex_guitar_input.cpp` passed checks for all three guitar subtypes, active-keyboard interference, merged button preservation and disconnect fallback. Its `--hardware` run passed with the actual connected guitar: player 1 subtype 6. `tests/probe_xinput.py` also recorded native subtype 6 in `docs/xinput_device_validation.json`; it required execution outside the sandbox to read physical XInput devices. Highway fret response after this fix still needs the user's hands-on check.

Build with `scripts/build_gpu_backend.ps1 -Windowed -Python <interpreter-path>`; launch using `Start-GH2.cmd`. The optional `GH2_TEST_INPUT` environment variable enables a controller fixture for bounded verification, with rows `seconds button-mask duration`; normal launches do not set it. `python tests/check_rex_runtime.py --windowed --seconds=95 --input=build/menu-input.txt` records windowed results.
